# PositionTracker: Plan Series

**Spec:** `docs/superpowers/specs/2026-10-30-possition-tracker-design.md`

The spec covers several independent subsystems, so it is implemented as a series of plans. Each plan ends with software that runs and is tested on its own.

| # | Plan | Delivers | Depends on |
|---|---|---|---|
| 1 | **Core tracking engine** (`2026-10-30-plan-1-core-tracking-engine.md`) | GPX course, map matching, laps, metrics, ETA, ranking, sector colours, alarm states, ingest API, live views and SignalR, demo simulator | none |
| 2 | **Accounts, events, registration** | PostgreSQL persistence (EF Core), organizer account and email sign-in, event creation, participant registration by the organizer, invitation emails from the own SMTP server (deliverability check first), confirmation, nickname and gender, token issue and re-issue | 1 |
| 3 | **Web app shell, i18n, themes** | React + Vite PWA, Slovak/English strings, light/dark theme tokens from the mockups, routing, API client, service worker | 1 |
| 4 | **Participant and organizer UIs** | Join flow, live participant screen with offline queue (IndexedDB), organizer dashboard and registration pages, GPX upload | 2, 3 |
| 5 | **Spectator UI, deployment, pilot** | Public spectator page, in-page finish alert, deployment to the home server behind the reverse proxy with HTTPS, rate limiting and hardening, pilot checklist | 2, 3, 4 |

Plans 2 to 5 are written after Plan 1 is reviewed, because their interfaces depend on what Plan 1 actually produces.
