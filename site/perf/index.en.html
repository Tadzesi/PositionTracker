Load test · home server · minutes of recording

What a 10-watt server sounds like when a race gets going.

PositionTracker follows runners live: phones send their position, the organizer and spectators watch the map. We measured the whole application on an Intel NUC as a system under test. We excited it with a step, stairs, an impulse and a chirp, and recorded 40 host channels at 10 Hz, plus the .NET runtime, PostgreSQL and every single request.

On the same 10 W NUC the fixed version carries the load of at least 6,000 phones (1,200 req/s, p99 0.2 s, zero errors). The original one fell apart already at 2,000 (400 req/s, 56 % errors). The application allows 2,000 participants, so the headroom is now threefold.

Fixes in the code

Five changes, each prompted by a specific chart from the measurement. The application's tests (Core, Data, Api) pass.

1

78bdfbf ETA from a table, not by stepping along the course

The arrival estimate walked the rest of the course in 100 m steps for every runner on every broadcast. It is now read from a precomputed table of one lap, so its cost does not depend on the course length. EtaEstimator. Building the view for 400 runners on 10 laps (benchmark on a PC): 53–70 ms → 8–11 ms.

2

78bdfbf The live view is computed outside the lock

Under the lock only the state is copied (positions, ranking, segments). The ETA, alarms and the view itself are built outside it, so position ingest waits only for the copy. EventRuntime.Capture. Ramp in the chart 100 ms → < 50 ms, p99 at 200 phones 121 → 18 ms.

3

78bdfbf Segment colours in one pass

The colour of each section (fastest, personal best) walked all results of the segment, so the cost grew with the square of the number of results. They are now computed once per broadcast in a single pass. SegmentBoard.Snapshot. It shows only in long lap races; this measurement does not quantify it on its own.

4

78bdfbf Device token cache

The server remembers a verified token for 10 minutes, so a request no longer waits for a DB connection. Revoking or reissuing a token takes effect immediately. DeviceTokenCache. DB connection queue on the stairs 726 → 0, mass start with known tokens p99 960 → 49 ms.

5

acaa272 Tokens of live races loaded in advance

A background service loads the tokens of every live race when it starts and after a server restart, and refreshes them every 5 minutes, so they never expire from the cache. DeviceTokenWarmer. Cold start of 1,000 phones: p99 3.86 s → 77 ms, DB queue 718 → 0.

i

How we verified it

We measured both versions with the same plan on the same machine, with a seed within the application's limit (10 laps). The first campaign had 400 laps, which inflated the ETA. New tests cover the ETA over several laps, segment colours, the cache and token preloading (against PostgreSQL).

The lock's fingerprint is gone

Original version: a request that arrives while the live view is being built waits until the build ends. The median forms a ramp long at the start of every 1.5 s cycle. The fixed version holds the lock only while it copies the state; the ramp dropped below the chart's resolution () and the median lies on the floor.

The same shows in the spectrum: the original version's latency has a line at the broadcast cycle (0.67 Hz) and its harmonics above the noise, the fixed one . What remains of the line is work that still runs on the cycle (serialising and sending the view), but it no longer blocks position ingest.

Above 1,490 phones (300 req/s) the same registered runners send more often than every 5 s. It is a load equivalent to more phones, not a larger registered field. The stairs end at the generator's maximum, not at the server's limit.

Mass start of 1,000 phones within one second: p99 response → (). The phones had been sending positions before the start, so the server knows their tokens.

Cold start: 1,000 phones the server has never seen (for example right after a restart). Without token preloading, 1,000 verifications went to the database at once: p99 , DB connection queue , errors. The server now loads the tokens of live races in advance and refreshes them every 5 minutes: p99 (), queue , errors .

Measured separately: idle and three starts of 1,000 phones each on the version with the token cache (78bdfbf) and with preloading (acaa272). The second start with preloading (p99 0.6 s) coincided with a scheduled job on the server that took 1.7 cores at the time.

Why: four causes, four numbers

The first campaign (sections 01–E7) ran with 400 laps of the loop, which is above the application's limit (10). The ETA estimate, which walked the rest of the course in 100 m steps, was therefore ~40× more expensive than in a real race, and the lock was held for ~1 s. The original figures below apply to this extreme. The comparison in this section uses a realistic race setup. Builds: original 68fceb1, fixed 78bdfbf.

02

Root cause: one lock and a 1.5-second cycle

synchronous averaging against the broadcast cycle

We placed every request by how much time had passed since the start of the last live-view build (the at timestamp is taken inside the runtime lock). It is the same technique as synchronous averaging against a once-per-revolution tacho pulse: everything tied to the broadcast cycle adds up, the rest averages out.

What the chart shows

A request arriving t seconds after the build started waits B − t. The median lies on a line with slope −1 and drops to the ~3 ms floor at B ≈ . That is how long EventRuntime.BuildLiveView holds lock (_lock).

Building the view for 400 runners (ranking, gaps, ETA, segments) takes about one second of the 1.5 s cycle on the Celeron. Meanwhile every Ingest waits for the same lock, so ~⅔ of the time the application does not accept positions. It is not a lack of CPU: in the idle phase with a full field only ~55 % of the CPU is busy, and still the median latency is 200 ms.

The same mechanism explains the gated ingest in the chirp (E4) and the broadcast lines in the spectrum (A1). Under load a second effect piles on: every request needs one DB connection (the device token lookup), so in saturation up to ~700 requests waited in the Npgsql pool at the peak.

Fixed (78bdfbf, acaa272): under the lock only the state is copied, the ETA is read from a table and device tokens are kept in memory. The before/after result is in 00b.

E1

Field size: what one runner costs

4 steps (400 registered: 98–390 active; 1,500 registered: 100–500) · each phone sends its position every 5 s

An analogue of order analysis: we do not change the request rate but the number of runners that have a position. Every 1.5 s the server builds the organizer's complete live view (ranking, gaps, ETA, segments) and sends it over SignalR.

Table

The first 30 s of each step are left out (transient).

On this HW, next to 37 other services, a race with 400 registered handles ~290 active phones (p99 1.3 s, no errors); at 390 it is already 34 % errors. A race with 1,500 registered handles ~250 active and collapses at 500 (76 % errors, p50 8.8 s).

Application CPU grows linearly with the number of active runners, almost equally in both races: by 1.5–1.8 ms of CPU per second for each runner. Per broadcast (1.5 s) that is ~2.2–2.7 ms of CPU per runner. A phone sends only 0.2 requests/s, so most of this work is not ingesting positions but recomputing the live view.

The cost depends not only on the number of active phones but also on the number registered: the organizer gets the whole field in every message. With 1,500 registered a LiveUpdate is ~0.7 MB even before anyone runs. The server's idle load without the test is ~0.7 of a core (other services).

The step barely shows in application CPU: before the step the application already spends ~0.65 of a core just on broadcasting the full field. The 78 req/s step adds only ~0.1 of a core. The response is carried by latency and errors instead: during the step requests got a 503 (a share of ), and the queue kept draining for s after the load was switched off.

The temperature behaves as a pure first-order system with τ ≈ 18 s and ΔT ≈ 3 °C. The coretemp sensor has a resolution of 1 °C, so the curve is stepped and the fit uses a 1 s mean.

E3

Capacity: stairs into saturation

90 s per stair · open loop · stop at p99 > 1.5 s or errors > 2 %

The generator sends requests at scheduled times regardless of the responses (open loop), so an overloaded server cannot hide its queues (no coordinated omission). Latency is measured on the server, in nginx, for every request.

Stairs

The first 15 s of each stair are the transient. A red row broke the criterion (p99 > 1.5 s or errors > 2 %).

Saturation came as early as the second stair. At 25 req/s p99 is 1.1 s with no errors; at 50 req/s there are 11 % errors (503 from the persistence queue) and p99 is 17 s. The sustainable capacity with 400 registered is therefore ~25 req/s, which corresponds to ~125 phones sending a position every 5 s. The E1 points (grey) lie lower, e.g. 60 req/s with p99 1.3 s. At that time, however, not every runner had a position yet.

The difference between E1 and E3 is the state of the field: E3 ran when all 390 runners already had a position. The live view is recomputed for the whole field (including runners who are not sending right now), so less time outside the lock is left for ingesting positions. The mean energy per request above idle power (including broadcasting the full field) is 70–90 mJ. The marginal energy of one request from the chirp (E4) is ~12 mJ.

E4

Transfer function: chirp and Bode plot

logarithmic sweep 1/400 → 1/4 Hz · 20 min

We modulated the load with a sine of rising frequency and identified the server as a system. The input is the request rate actually sent; the outputs are CPU, power and temperature. Since the instantaneous phase of the excitation φ(t) is known, we estimate the transfer with a tracking filter (lock-in, as in order tracking): at each of 40 frequencies we fit both input and output with sin φ and cos φ over a window of at least 4 periods. H = Y/U, the band is ±2σ of the amplitude estimate, and the fit's R² shows what share of the output's variance the excitation explains.

What follows from it

The application has a flat transfer of ~1.5 ms CPU per request with a phase around 0° across the whole 0.006–0.2 Hz band. It is a static (memoryless) system: the CPU responds to load immediately. Platform power responds marginally with ~12 mJ per request (median, range 8–36 mJ). The mean above idle in E3 (70–90 mJ) is higher because it also includes broadcasting the full field.

R² is low because the response to the ±20 req/s excitation is buried in the broadcast's "noise" (±0.5 of a core at 0.67 Hz) and that of the other services. Individual points are therefore uncertain (median R² 0.004, phase from −40° to +80°). Only the summary over 40 frequencies is reliable: median 1.5 ms/req and phase −2°, much as in a low-SNR measurement with averaging.

Temperature: the step gives a first-order model (τ ≈ 18 s, fc ≈ 0.009 Hz, static gain ~0.04 °C/(req/s)). A chirp with ±20 req/s amplitude, however, changes the temperature by only tenths of a degree, below the sensor's quantisation step (1 °C). The measured ~0.014 °C/(req/s) is therefore three times below the model already under fc and does not fall above fc. With this excitation the temperature channel is at the limit of the instrument's resolution.

Phase portrait on the left: the power → temperature trajectory during the chirp. Slow cycles open into a hysteresis loop (temperature lags behind power).

E5

Impulse: mass start

the whole field (390 phones) within one second · 3 repetitions · averaging

The starter's gun: every phone sends its position in the same second. We repeated the impulse three times and averaged the responses, as in an impact hammer test.

Individual impulses (latency as seen by the phone)

The server survived the whole field (390 phones) within one second: it accepted 99 % of positions and only 1–3 requests got a 503. The queue, however, took 4.6–7.8 s to drain, and the median latency jumped between 1.1 and 5.5 s depending on which phase of the broadcast cycle the impulse hit. The three repetitions therefore differ more than noise would suggest. Moreover, the responses do not arrive smoothly but in batches ~1.5 s apart: the queue drains only in the gaps between view builds, when the lock is free.

E6

Spectators: SignalR fan-out

0 → N spectators · constant position ingest

Every spectator receives the public view of the race over a WebSocket. As the number of spectators rises we watch where the network, the CPU or the broadcast cycle breaks.

Spectators are almost free for the CPU: 100 spectators added ~0.05 of a core to the application, because SignalR serialises a message for a group only once. Bandwidth is what costs: the public view is ~220 kB and goes out 0.67× per second, so each spectator costs ~0.15 MB/s. 100 spectators ≈ 15 MB/s ≈ 120 Mbit/s, which is more a limit of the home line and the Cloudflare tunnel than of the NUC.

The ~31 s delay is the configured spectator delay (30 s) plus ~1 s delivery. The steps with 5, 35 and 75 spectators have higher total CPU and p99, but the application's CPU does not change: it is background from the server's other services. The sweep ended at the planned maximum (100); no limit was reached.

A1

Spectral analysis

CPU sampled at 10 Hz · Nyquist 5 Hz

A server that "does nothing" has a rich spectrum: every periodic task (the broadcast cycle, neighbouring services, our own measurements) shows up in it as a line. The spectrogram of the whole run is the analogue of a Campbell diagram. With 400 runners the view build (~1 s) does not yet exceed the cycle, so the broadcast line stays at 0.667 Hz. With 1,500 runners in the first run the period stretched to as much as 1.7 s.

During the race 0.667 Hz dominates (the 1.5 s broadcast cycle) with harmonics 2×, 3×, 5× and 6×. The sawtooth load (≈1 s of work, 0.5 s of rest) has rich higher harmonics, exactly like a rectangular signal with a ⅔ duty cycle.

The spectrum also gave the neighbours away. The line at ~11.5 s (0.088 Hz) with harmonics belongs to the MQTT broker, which at this rate loads one core for ~1 s (confirmed by a per-container CPU measurement after the test). The recording ("other services") also shows blocks exactly every 300 s, alternately ~30 and ~80 s long at ~1.25 cores: a scheduled job on the host that searches the system journal (identified by a later process measurement). The 1 Hz lines at idle come from our own 1 s measurements.

A2

Latency

server (nginx) · end-to-end (phone → organizer)

10 probe phones send a position every 5 s. We measure the time from sending a position to its first appearance in the organizer's LiveUpdate. It therefore includes waiting for the next broadcast (sample and hold). The stepped CDF at idle arises because the 5 s probes and the 1.5 s cycle are in a 10 : 3 ratio, so the probes hit only 3 distinct phases of the cycle (a stroboscopic effect).

The load generator ran on a PC connected over Wi-Fi. Primary latency is therefore measured on the server, and we report Wi-Fi as a separate channel of instrument noise.

The heatmap has no bell but a band from ~3 ms to ~1 s of uniform density. That is the lock's signature: waiting is uniformly distributed between 0 and B. End-to-end: at idle with an empty field p50 0.80 s, almost exactly half of the 1.5 s cycle (pure sample and hold). During the race p50 1.8 s and p99 3.7 s = waiting for the lock + waiting for the next cycle + ~1 s build + delivery.

A3

Jitter and neighbours

what the test did to the rest of the household

The same machine runs Home Assistant, the DNS for the whole network and public websites. A 1 kHz loop measures how late the scheduler wakes it up (much like cyclictest). A 2 Hz DNS probe also served as the test's kill switch (6 queries in a row over 250 ms → stop).

Scheduler jitter is the same in every regime: p99 ~0.75 ms, max 7–9 ms. The network-wide DNS answered at p50 0.4–0.9 ms and p99 up to 4.3 ms, not a single query was lost and the kill switch never fired. The test did not restrict the rest of the household.

The application is limited by the lock, not by the CPU. Even in saturation it does not load both cores enough for the scheduler to suffer. Wi-Fi between the PC and the server: p50 1.45 ms, p99 21 ms, max 270 ms, 5 lost out of 64,567 pings. That is why the primary measurement is on the server.

A4

Correlations: what drives latency

GC is not the culprit

During the 30-minute race all GC pauses together took 4.6 s (0.25 % of the time) over 182 gen0 and 56 gen2 collections. The correlation of GC pauses with p99 is weak (r ≈ 0.13). The broadcast period correlates more strongly (r ≈ 0.29).

So latency is driven by synchronous work under the lock, not by memory management. At 1 s resolution, moreover, the correlation with the 1.5 s cycle is partly smeared (aliasing); the direct evidence is the phase-resolved chart in section 02.

M

Methodology and instruments

Setup

A separate test stack (the same image as production, its own database, simulated e-mails) on a separate port of the same home server, outside Cloudflare. Production data was not touched.

  • Generator: our own .NET 10 tool LoadLab on a Windows PC. A scheduler on a dedicated thread integrates the target rate R(t) (open loop) and measures latency from the scheduled send time.
  • Race: 400 confirmed runners with their own tokens (1,500 in the 1st run), 10 of them probes. Positions lie on a real loop (5.7 km, Žilina) and speeds are 2.4–4.6 m/s.
  • Comparison (00b): 1,500 runners, 10 laps (the application's limit), the same plan against two application images (68fceb1 and 78bdfbf). The cold start separately against 78bdfbf and acaa272. Every run had a fresh database.
  • Host: a Python sampler on an absolute 10 Hz schedule. It reads cgroup v2, /proc, RAPL (package, core, psys), hwmon, PSI and diskstats.
  • .NET: dotnet-counters in a sidecar container (shared PID namespace, diagnostic socket), 1 s.
  • PostgreSQL: pg_stat_database/wal/checkpointer via psql \watch 1.
  • nginx: a CSV log with $request_time and $upstream_response_time for every request, an X-T header with the server time.

Time synchronisation

PC clock against the server: offset ms and drift ppm (≈19 ms per hour). A linear correction leaves a residual of ms. The estimate comes from the fastest responses in 10-minute windows (X-T header, middle of the RTT). All channels are on the server's time axis.

Limitations: the generator ran over Wi-Fi (client latency carries network noise, so the primary data comes from the server). During the test the server also served normal household traffic. The sampler, the jitter loop and the measuring sidecars ran on the same machine, and we did not quantify their consumption separately (their 1 s cycle is visible in the spectrum). Apart from the impulses, each experiment ran once; spread is reported within a stair.
